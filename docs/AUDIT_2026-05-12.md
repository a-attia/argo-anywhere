## CRITICAL findings (fix before any user-facing release)

### C1. `argo_opencode.sh` symlink can be served as text on compute nodes (Bug 1 root cause)
**SEV: CRIT**. Sections: file layout + Section 15 (`remote_bootstrap`).

The repo ships `argo_opencode.sh` as a `mode=120000` git symlink whose blob
content is the literal 16-byte string `argo_anywhere.sh\n`. Three failure
modes produce a working-tree file with exactly that content:

1. **`git clone` with `core.symlinks=false`** (Windows default; sometimes set
   by hardened Linux configs) — git materializes the symlink as a plain
   file containing the link target text. `bash argo_opencode.sh` then runs
   `argo_anywhere.sh` as a command on line 1.
2. **`scp` of the symlink itself** without `-L`/dereference — modern
   OpenSSH scp follows source symlinks by default, but legacy tools
   (`rsync` without `-L`, `cp` without `-L`, archive tools without
   `--dereference`) preserve symlink-ness, which on platforms that
   don't support symlinks materializes as a text file.
3. **NFS or filesystem with disabled symlinks** — same outcome as (2).

The user's `bash argo_opencode.sh: line 1: argo_anywhere.sh: command not
found` on compute-386-01 was almost certainly path (1) or (2).

**Why `remote_bootstrap` doesn't help**: Line 1667 uses
`self="${BASH_SOURCE[0]}"` then `scp "$self" ...` (line 1695). On the
LAPTOP with proper symlinks, BASH_SOURCE[0] = `argo_opencode.sh` (the
symlink) but `scp` follows the symlink and transfers the real bytes.
Good. **But Bug 1 is on the compute-node side**: a user who got the
file there via the broken paths above and then runs `bash
argo_opencode.sh` server-side hits the failure before any of our code
runs.

**Fix candidates**:
- A. Add a self-heal at line 1 of the script: if the script's first
  line looks like a filename (no shebang, just a filename), die
  loudly with a "your file got demangled; re-curl" message.
- B. Document loudly in README that users must `curl` and never
  `git clone` (and certainly never `scp` the symlink).
- C. Stop using symlinks; ship N copies of the script with one-line
  patches for the per-client default. Loses single-source-of-truth.
- D. Combination: A + B (defensive code + clear docs).

**Recommended**: D. The self-heal catches users who get bitten despite
documentation; the docs reduce the population that gets bitten.

### C4. SSH failure lock fails-open if state dir doesn't exist
**SEV: CRIT — CSPO**. Section 9 (`ssh_attempt_fail`).

Lines 779-781:
```bash
mkdir -p "$STATE_DIR" 2>/dev/null || true
date +%s > "$SSH_FAIL_LOCK_FILE" 2>/dev/null || true
```

If `mkdir -p` fails (read-only `$HOME`, full disk, permission denied,
NFS hiccup), the lock file isn't written. The `|| true` swallows the
error. The in-memory `_SSH_LOCKED=1` is set, so the CURRENT run's
remaining attempts are blocked — but the next `bash argo_opencode.sh`
invocation has no on-disk lock to read, so its `_SSH_FAIL_COUNT`
starts at 0 and gets to make THREE MORE failed attempts before locking
again. **Indefinite re-runs = unlimited failed auths.**

**The ENTIRE point of the on-disk lock is to defend against CSPO across
restarts.** Letting it silently fail to persist defeats the purpose at
exactly the moment the defense is most needed.

**Fix**: if the lock can't be persisted, REFUSE TO MAKE ANY MORE SSH
ATTEMPTS in this run. `die` hard with a "cannot persist failure lock;
fix STATE_DIR before continuing" message. Better to halt the user
than to hammer CSPO.

### C5. Lock TTL of 5 minutes is too generous for CSPO defense
**SEV: CRIT — CSPO**. Section 9 (`SSH_FAIL_LOCK_TTL=300`).

After the lock expires, the user gets THREE FRESH attempts before
re-locking. Under `SSH_FAIL_LOCK_TTL=300`, that's 3 attempts every 5
minutes = **36 attempts/hour**. CSPO blocks at roughly 10/hour
(approximate; ANL's exact threshold isn't published).

A user with a permanently-broken SSH key (e.g. wrong username) who
re-runs the script every 5+ minutes for an hour will trigger CSPO
despite the "defense".

**Fix**:
- Increase TTL to 30 min (matches CSPO's typical decay window better).
- After the lock auto-expires, START THE COUNTER AT THRESHOLD-1, not 0.
  That way the user gets ONE more attempt before re-locking, not three.
- Add an exponential backoff: each successive lock-event doubles the
  next TTL (5min → 10min → 20min → 40min, capped at 24h).

### C6. mode_server's "existing argo-proxy is ours; reusing" silent return (Bug 2 candidate root cause)
**SEV: CRIT — bug**. Section 18 (line 3281).

```bash
3257: listener_pid="$( { lsof -nPi ":${PROXY_PORT}" -sTCP:LISTEN -t 2>/dev/null || true; } | head -n1)"
...
3266: if curl -fsS --max-time 2 "http://127.0.0.1:${PROXY_PORT}/health" >/dev/null 2>&1; then
...
3280:       ok "Existing argo-proxy already serving on 127.0.0.1:${PROXY_PORT} (pid ${listener_pid}); reusing."
3281:       return
```

If `lsof` finds a listener owned by us AND `curl /health` succeeds,
mode_server returns 0 IMMEDIATELY without verifying the listener is
actually `argo-proxy`. Two failure modes:

1. **Race**: process dies between the lsof check and the parent's
   subsequent curl. The user reports exactly this: mode_server said
   "reusing", returned silently, and a moment later `status` showed
   no listener.
2. **Wrong process**: any user-owned process bound to `${PROXY_PORT}`
   that happens to respond to `/health` (e.g. a generic web server with
   a /health endpoint) is mistaken for our argo-proxy.

**The user's Bug 2 transcript shows mode_server returning silently
after `[ ok ] argo-proxy config already up to date`** — this is
consistent with the line 3281 `return` firing.

**Fix**:
- Verify the process is actually argo-proxy (check `ps -p $pid -o comm=`).
- Add a verbose log at line 3280 so the user sees what was reused.
- After returning, the in-process caller's verification curl (line
  2784) MUST handle the race: if our "reused" proxy is gone by the
  time we check again, log loudly + bootstrap a fresh one rather than
  die.

### C7. Reconnect loop in `monitor_tunnel_loop` bypasses SSH attempt tracker
**SEV: CRIT — CSPO**. Section 16 (lines 1937-2079).

The reconnect path (`ssh -O check`, `ssh -N -L`) does NOT go through
`ssh_attempt_pre/ok/fail`. Comments at lines 720-723 acknowledge "the
common reconnect path does NOT re-auth (the multiplex master holds
the connection)". This is true for SHORT outages, but:

- If the master dies (laptop closed past `ControlPersist=3600s`,
  network outage past `ServerAliveCountMax × ServerAliveInterval = 60s`),
  the `ssh -N -L` at line 2001 WILL re-auth.
- `RECONN_BURST_LIMIT=3` within `RECONN_WINDOW_SEC=60` caps the rate
  to 3/min, then 30s pause. Sustained: ~2 attempts/min = **120
  attempts/hour**. Far above CSPO's threshold.

**The single most likely path to a CSPO block for a working-config
user** is leaving the script running while the network or proxy
flaps for an extended period.

**Fix**:
- Wrap `ssh -N -L` reconnects in `ssh_attempt_pre/ok/fail`. After 3
  consecutive reconnect failures, escalate to the same lock as
  preflight (write to disk, refuse further attempts).
- Increase the burst-pause to 5 min (currently 30s); after 3 bursts,
  stop reconnecting entirely and notify the user.

### P1. SIGPIPE in `lsof | head -n1` cmd-substitution silently kills the script (FOUND DURING PHASE 1 LIVE-TEST)
**SEV: CRIT — bug, root cause of "Bug 2" / on-node bootstrap silent-fail**.

Three sites use the pattern:
```bash
local x; x="$(... | head -n1)"
# OR
x="$(... | head -n1)"
```

Under `set -euo pipefail`:
1. `head -n1` reads its first line and closes stdin
2. The upstream `lsof` (or `awk`) gets SIGPIPE and exits non-zero
3. `pipefail` makes the pipe's overall exit code non-zero
4. The assignment `x="$(...)"` propagates the non-zero exit
5. `set -e` kills the script SILENTLY with no error message

**Affected lines**:
- `argo_anywhere.sh:2311` — `local_tunnel_status` `pid` lookup
- `argo_anywhere.sh:2581` — `ensure_or_reuse_tunnel` SSH_TUNNEL_PID capture
- `argo_anywhere.sh:3550` — `mode_server` `other_argoproxy_port` detection
  (**root cause of the bootstrap silent-fail reported on compute-386-01**)

**Symptoms**:
- bootstrap exits silently after `[ ok ] argo-proxy config already up to date`
- no error message on the node
- laptop side reports `Server bootstrap on <node> failed`
- server.log shows the same lines repeated (each retry hits the same set -e
  exit; the laptop just sees non-zero and reports failure)

**Why this didn't reproduce in initial Phase 1 test 8c**: the existing
argo-proxy was healthy, so the script `return`'d at line 3514 (the reuse
branch) BEFORE reaching the vulnerable line 3550. The bug only fires when
no listener exists OR the listener is unhealthy AND the user has another
argo-proxy on a different port that lsof might enumerate.

**Fix** (applied as hotfix in commit AFTER Phase 1):
```bash
x="$( { ... | head -n1; } || true )"
```
The `{ ...; } || true` wrapper swallows SIGPIPE so the assignment can't
trip set -e. Drop-in fix; doesn't change semantics.

**Why this audit class will recur**: the `local x; x="$(... | head)"`
pattern is bash idiom but interacts dangerously with `set -euo pipefail`.
Future code reviews must check every `$(... | ...)` cmd-substitution for
SIGPIPE susceptibility.

## HIGH-SEVERITY findings

### H1. SSH preflight in `--no-mfa` mode tries node directly without ProxyJump
**SEV: HIGH — CSPO**. Section 13 (lines 1468-1469).

```bash
if ssh -o BatchMode=yes -o ConnectTimeout=5 -o StrictHostKeyChecking=accept-new \
     "${user}@${target}" true 2>/dev/null; then
```

No `$(ssh_args ...)` — so no `-J jumphost`. If the user is OFF the ANL
network and runs with `--no-mfa --node compute-X`, this attempts a
direct connect (no jump host). Off-network the host is unreachable;
ssh times out; the SSH attempt counter increments. Three runs = locked
+ contributes to CSPO failures.

**Fix**: include `$(ssh_args "$user" "$target")` in the BatchMode
preflight unless `target == ANL_JUMP` (current jump-loop guard
already handles that).

### H2. pick_node interactive hostname loop has no per-session retry limit
**SEV: HIGH — CSPO**. Section 14 (lines 1611-1647).

User can type as many bad hostnames as they want; each failed
`ssh_reachable` consumes a CSPO attempt. The `_SSH_LOCKED` check at
line 1642 fires after 3 failures (matching the global counter).
**A confused user can rack up multiple attempts before the lock.**

**Fix**: add an explicit max-iterations (e.g. 5 per pick_node call),
warn the user before it triggers. Alternatively: make the
`ssh_reachable` test optional ("warn but allow") so a typed hostname
that's just unreachable in the moment doesn't burn the counter.

### H3. `--probe-nodes` makes `len(ANL_NODES)` SSH attempts in a tight loop
**SEV: HIGH — CSPO**. Section 14 (lines 1543-1558).

With 10 ANL_NODES, a broken-auth user makes 3 attempts (lock fires)
before the loop bails. Defense exists at line 1554 but only AFTER the
3 attempts. Better to gate the FIRST attempt with `ssh_attempt_pre`
and only continue probing if it succeeds.

**Fix**: add `ssh_attempt_pre` at the top of the for-loop body.

### H4. `find_next_free_remote_port`'s remote one-liner can run unbounded
**SEV: HIGH — CSPO + bug**. Section 16 (lines 2230-2240).

The remote inline script:
```bash
p=${start}
while [ "$p" -le ${end} ]; do
  if ! lsof ... ; then echo $p; exit 0; fi
  p=$((p+1))
done
exit 1
```

Default range is 100 ports (`start` to `start+100`). With every-port-
busy, walks all 100 in one ssh session. Single ssh call so ONE
ssh_attempt_pre/ok/fail cycle. Acceptable.

But: **no upper-bound check on `start`/`end` in the remote script**.
If the caller passes `start=64742 end=70000` (5258 ports), the remote
loop walks all of them. Doesn't increment ssh counter (single call)
but holds an ssh session open for tens of seconds.

**Fix**: clamp the remote range to a reasonable max (e.g. min(end-start, 200)).

### H5. `argo-proxy reuse` check uses `curl /health` without identity check
**SEV: HIGH — bug**. Section 18 (line 3266).

`curl /health` returns 200 from ANY healthy argo-proxy on that port,
including one configured for a DIFFERENT Argonne user. The line 3275
config-user check defends against this AFTER the curl decision, but if
the config.yaml is missing or unreadable, the check passes (line 3275
condition: `[ -n "$cfg_user" ] && [ -n "$want_user" ] && [ "$cfg_user"
!= "$want_user" ]` — when `cfg_user` is empty, the condition is false
so we fall through to "reusing").

**Fix**: invert the check. If `cfg_user` is empty when we expected to
find a config (proxy was running so config should exist), refuse to
reuse with a clear "config inspection failed; refusing to attribute
calls" message.

### H6. `setup_claudecode_client`'s scope detection runs AFTER install but before user could be authenticated
**SEV: HIGH — bug**. Section 12 (line 1276).

`claudecode_pick_scope` checks `~/.claude.json` (the OAuth state).
But `setup_claudecode_client` calls `ensure_claudecode_installed`
FIRST (line 1390), then `claudecode_pick_scope` (line 1391). On a
fresh install, `~/.claude.json` doesn't exist yet (the user hasn't
auth'd to their personal account). So scope defaults to GLOBAL,
writing to `~/.claude/settings.json`. **If the user later does
`claude auth login`, our env block survives but the OAuth token gets
written to `~/.claude.json`. Both coexist. The OAuth token in
`~/.claude.json` apparently takes precedence over `ANTHROPIC_AUTH_TOKEN`
in settings.json** (per Anthropic's docs).

So our config silently loses effect once the user auths. They'll
think the proxy is in use but they're actually using their personal
account.

**Fix**: either (a) default to PROJECT scope always (safer) and let
`--scope global` opt in, OR (b) check `claude auth status` to detect
existing auth, OR (c) document the gotcha loudly.

### H7. Identity write in `ANTHROPIC_AUTH_TOKEN` leaks ANL username into shareable file
**SEV: HIGH — privacy**. Section 12 (line 1376).

```python
env["ANTHROPIC_AUTH_TOKEN"] = user
```

The user's ANL username gets written into `~/.claude/settings.json` or
`./.claude/settings.local.json`. Both files are commonly committed to

**Fix**: warn the user about this in the post-write log message;
suggest they add the file to their `.gitignore`. Document in the

### H8. `ssh -O exit ... x` on cleanup tries to connect to host literally named "x"
**SEV: HIGH — CSPO (mild)**. Section 9 (line 838).

```bash
ssh -O exit -o "ControlPath=${sock}" x 2>/dev/null || rm -f "$sock"
```

The hostname "x" is required because `ssh -O exit` needs a destination.
IF the master socket is gone but the file still exists (stale), `ssh
-O exit` may fall back to a normal connection to "x" (which is some
random hostname or fails). Doesn't go through ssh_attempt_*.

**Fix**: use `ssh -O exit -S "${sock}" placeholder` — `-S` is the
explicit socket flag; the hostname is purely positional, never
contacted. Or pre-check: `[ -S "$sock" ]` then run; else just `rm`.

### M6. `ensure_or_reuse_tunnel`'s `xargs -n1 kill` could kill foreign processes
**SEV: MED — bug**. Section 16 (line 2406).

```bash
lsof -nPi ":${PROXY_PORT}" -sTCP:LISTEN -t 2>/dev/null | xargs -n1 kill 2>/dev/null || true
```

This kills ANY process listening on PROXY_PORT, not just our ssh tunnel.
The classification before this branch claimed "ours-unhealthy-fg" so
SHOULD be ours, but if classification is wrong (e.g. some other ssh -L
from a different script), we kill it.

**Fix**: kill only the specific PID detected, and double-check the
process command line matches the ssh -L pattern before killing.

---

### M7. `local_tunnel_status` mux detection regex is fragile
**SEV: MED — bug**. Section 16 (line 2154).

```bash
*ssh:*argo-opencode-*\[mux\]*)  kind="mux" ;;
```

Matches the `ps -o command=` output of an ssh master process. The
exact format of `ps`'s ssh process display varies between OS versions
(macOS Big Sur+ shows `ssh: <socket-path> [mux]`; older shows just
`ssh`). If the format changes, classification fails silently (returns
"other-or-broken" for our own master) which causes refusal to reuse.

**Fix**: more permissive match; or rely on socket file presence
instead.

---

### M8. `setup_claudecode_client` writer doesn't validate JSON before merging
**SEV: MED — bug**. Section 12 (line 1352).

If `~/.claude/settings.json` is malformed JSON (e.g. user manually
edited and broke it), the Python heredoc returns empty `data={}` and
**writes a fresh file with only our env keys, silently destroying the
user's broken-but-recoverable config**.

**Fix**: when JSON parse fails, refuse to merge; print a loud error
asking the user to fix the file or pick `[k]` at the prompt.

---

### M9. `write_argoproxy_config` PyYAML fallback writes hardcoded defaults
**SEV: MED — bug**. Section 18 (lines 2974-2982 + 3018-3025).

If PyYAML is missing, the script writes a 6-key config from scratch.
Any custom keys the user had (e.g. `argo_embedding_url`, `concurrent_downloads`)
are **silently lost** if the user picks `[b]ackup`. The warning
mentions this but the user might miss it under time pressure.

**Fix**: either die hard if PyYAML is missing (instead of writing
defaults), or refuse `[b]` choice in the merge dialog when fallback
mode is active.

---

### M10. `ask()` reads from stdin without TTY check
**SEV: MED — bug**. Section 3 (lines 205-206).

```bash
ask()  { local p="$1" def="${2:-}" reply; printf '%s%s%s ' "$C_YLW" "$p" "$C_OFF" >&2;
         read -r reply || true; printf '%s' "${reply:-$def}"; }
```

When stdin is not a TTY (e.g. script piped from `curl | bash`, or
under a non-interactive automation), `read` reads from whatever pipe
is connected (which may be the script body itself, eating script
content). The `|| true` swallows the failure. The default value is
returned silently. **In tee'd re-exec scenarios this can lead to
unexpected default selections.**

**Fix**: detect non-TTY stdin and either die (interactive mode required)
or always use the default with a log line.
